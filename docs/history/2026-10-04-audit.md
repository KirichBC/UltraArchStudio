# Анализ UltraArch Studio — 4 октября 2026

> Исторический документ. Актуальные файлы и сборка описаны в [главном README](../../README.md).

Проект имеет разумное разделение на анализ контента, генерацию параметров, управление процессами, сборку архива и GUI. Использование внешнего 7-Zip, сохранение победившего архива и удаление проигравших кандидатов — удачные решения. Однако несколько заявленных возможностей реализованы частично, а ошибки в ограничении памяти, обработке входных данных и финализации требуют исправления до расширения поиска.

Анализ выполнен без изменения исходного кода. Сборка и проверочные файлы размещены в `/private/tmp/ultraarch-audit-build` и `/private/tmp/ultraarch-audit-fixtures`. Windows-ветка изучена статически; на Windows приложение не запускалось. Каталог проекта не содержит Git-репозитория.

**Приоритет 0: аварии, память и сохранность результата**

1. **Переполнение в PE-парсере вызывает аварийное чтение памяти.**

   Место: `src/core/ContentAnalyzer.cpp:42–45`. Выражение `peOffset + 4` вычисляется в `uint32_t`. При `e_lfanew = 0xFFFFFFFC` сумма становится нулём, проверка границ проходит и происходит чтение далеко за пределами буфера. Воспроизведено на 512-байтовом файле с MZ-заголовком под ASan: процесс завершился с ошибкой чтения памяти.

   Исправление: читать little-endian offset без приведения указателя к `uint32_t*`; после проверки минимального размера сравнивать `offset <= bytesRead - 4`. Проверять архитектуру PE отдельно: наличие PE-сигнатуры само по себе не означает x86/x64.

2. **GUI завышает RAM-лимит в 1024 раза.**

   Места: `src/ui/MainWindow.cpp:589`, `:616`, `:670`. Ползунок содержит гигабайты, поле называется `ramLimitMB`, но используется умножение на `1024 * 1024`. Выбор 8 ГБ передаёт 8 388 608 МБ вместо 8192 МБ. Обратное преобразование встроенного пресета 8192 МБ даёт 0 ГБ.

   Исправление: единое преобразование GiB → MiB через множитель 1024; валидация диапазонов после CLI, GUI и загрузки пресетов. Желательно типизировать единицы памяти, чтобы исключить подобные ошибки.

3. **Общий бюджет памяти не обеспечивается.**

   Места: `src/core/OptimizerEngine.cpp:498–501`, `src/core/ResourceGuard.cpp:40–48`, `src/core/ProcessManager.cpp:312–348`. Каждый worker получает полный лимит. При 4 workers и 8 ГБ потенциально допускается около 32 ГБ только для компрессоров. В Windows дважды указан `JOB_OBJECT_LIMIT_PROCESS_MEMORY`; `JOB_OBJECT_LIMIT_JOB_MEMORY` отсутствует. В POSIX значение `limitMB` вычисляется и не применяется. Ошибка `attachProcess()` игнорируется.

   Исправление: планировщик резервирует память перед запуском кандидата и освобождает после завершения. Один общий Windows Job Object ограничивает всю группу компрессоров, дополнительно задаются ограничения процессов. Для Linux — отдельная реализация ограничений с учётом возможностей системы; для macOS — явно описанные возможности и ограничения защиты. Не считать RLIMIT_AS полным аналогом лимита физической RAM. Сбой подключения защиты должен становиться диагностируемым результатом.

   Microsoft различает лимит одного процесса и лимит всего Job Object: [JOBOBJECT_EXTENDED_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information).

4. **CLI сообщает успех после провала финальной сборки.**

   Место: `src/main.cpp:266–275`. Успех определяется наличием лидера, хотя копирование/сборка результата могли завершиться ошибкой. Воспроизведено с выходом в несуществующий каталог: вывод содержит `Error copying candidate`, файл отсутствует, код завершения — 0.

   Исправление: явный итог выполнения: Completed / Failed / Cancelled, код ошибки и фактические выходные файлы. Возвращать 0 только после успешной финализации.

5. **Существующий результат удаляется до подготовки нового.**

   Места: `src/core/ArchiveAssembler.cpp:63–67`, `:96–98`. Если запись или проверка нового архива не удались, старый файл уже потерян. Не проверяется совпадение input/output и опасное расположение scratch внутри входной папки.

   Исправление: собирать результат в уникальный staging-файл рядом с выходом, проверять, затем заменять существующий результат средствами платформы. Для томов учитывать весь набор файлов. Проверять пути до запуска и исключать scratch/output из входного manifest.

**Приоритет 1: соответствие настроек фактическому результату**

6. **Разбиение на тома и явный solid-блок игнорируются при reuse.**

   Места: `src/core/OptimizerEngine.cpp:465–469`, `src/core/ArchiveAssembler.cpp:60–92`. Кандидаты получают пароль и `-mhe` ещё в `TaskMatrixGenerator.cpp:195–199`, поэтому шифрование в обычном пути сохраняется. Но `volumeSizeMB` и пользовательский `solidBlockSize` в кандидатах отсутствуют, а reuse обходит применение этих параметров.

   Воспроизведение: `--volume 1` на файле 2 МиБ создаёт единственный `volume.7z` размером 2 097 282 байта, без `.001`/`.002`.

   Исправление: сравнивать полную спецификацию кандидата и выхода перед reuse. При несовпадении выполнять финальную сборку. В ветке реальной сборки тома следует проверять через первый том и возвращать список созданных файлов; сейчас код проверяет базовый путь. SFX-модуль передавать явным путём, отсутствие нужного модуля считать ошибкой выбранного режима.

7. **Препроцессинг не связан с тестированием и сборкой.**

   Места: `src/core/OptimizerEngine.cpp:314–353`, `:553`; `src/core/PreprocessorPipeline.cpp:98–125`. Пайплайн запускается до создания `m_tempDir`. В первом запуске путь пустой; последующие запуски тоже не имеют гарантированно корректного workspace. Обработанные данные появляются в `step_*`, но пайплайн возвращает только статистику. Координатор выбирает `preprocDir`, workers продолжают читать исходный input либо исходную распаковку, а анализ не обновляется.

   Исправление: создать RunContext/workspace до распаковки и препроцессинга; вернуть `effectiveInputPath` вместе со статистикой; использовать один manifest во всех фазах и повторно анализировать изменённые данные. Очищать все принадлежащие запуску каталоги через RAII, в том числе при ошибках.

   Разделить битовую идентичность исходников и оптимизацию ресурсов. Leanify/ECT могут менять файл при сохранении его содержимого на другом уровне; `7z t` проверяет целостность архива, но не идентичность оригиналу. Для Precomp/SREP нужен явный обратный пайплайн восстановления; текущий код такого контракта не реализует.

8. **Восстановление сессии фактически отсутствует.**

   Места: `src/core/OptimizerEngine.cpp:356–363`, `:648–661`, `src/core/SessionManager.cpp:24–33`, `:121–138`. После сообщения о resume очередь не фильтруется и лидер не восстанавливается. Каталог сессий в engine не инициализируется. Сохраняются лишь несколько полей; нет результатов, полного settings, сохранённого архива и идентификации входного набора. При checkpoint не заполняются output/settings. Несколько workers могут одновременно перезаписывать один JSON.

   Исправление: версионированная схема, проверка fingerprint входа/настроек/версии инструмента, сохранение результата и архива лидера, один writer с атомарной заменой checkpoint. Не удалять материалы, необходимые для resume, при отмене или ошибке.

9. **Управление потоками и GUI содержит гонки и проблемы времени жизни.**

   Места: `src/core/OptimizerEngine.cpp:531–532`, `:568`, `:600–601`; `src/ui/MainWindow.cpp:74–119`; `src/main.cpp:656–657`. Один skip token общий для всех workers: новый worker сбрасывает отмену, предназначенную другому. Проверка архива выполняется под общим mutex без отмены; UI-запросы результатов могут ждать всю проверку. Pause останавливает выдачу следующего задания, но активные процессы продолжают работу. В цикле ожидания паузы не учитывается Assemble Best.

   State callback записывает обычные GUI-поля из координатора, а GUI читает их без синхронизации. Кроме того, MainWindow создаётся после engine и уничтожается раньше него, но engine сохраняет callbacks с захваченным `this` и вызывает их при собственной деструкции. Это создаёт обращение к уничтоженному объекту; закрытие GUI требует отдельной проверки.

   Исправление: неизменяемые настройки на запуск, токен отмены запуска плюс отдельные токены задач, event queue для GUI, выполнение процессов/проверки вне mutex, короткая блокировка только при публикации результата. При закрытии сначала остановить и join engine, затем отписать callbacks и уничтожить UI. Определить точную семантику паузы и пропуска при нескольких workers.

10. **Пароли сохраняются и отображаются открыто.**

    Места: `src/core/PresetManager.cpp:280`, `src/core/OptimizerEngine.cpp:395–397`, `src/ui/LeaderboardWidget.cpp:33`, `:48`, `src/core/ArchiveAssembler.cpp:159–162`. Пароль входит в flagsStr, показывается в таблице и экспортируется, а пресеты содержат его в JSON. В пересборке полная команда с паролем попадает в лог.

    Исправление: отделить секрет от отображаемых флагов, маскировать при логировании/экспорте, не включать в обычные пресеты. Если сохранение пароля нужно пользователю — применять системное хранилище секретов. Ограничение передачи пароля внешнему процессу описать отдельно.

**Где оптимизация даст наибольший эффект**

11. **Заменить автоматический Store по энтропии проверкой сжимаемости.**

    Места: `src/core/ContentAnalyzer.cpp:137–140`, `src/core/TaskMatrixGenerator.cpp:100–112`. Энтропия отдельных байтов не учитывает повторяющиеся последовательности. Проверялся файл из случайного блока 64 КиБ, повторённого 256 раз:

    | Результат | Байты |
    | --- | ---: |
    | Исходный файл | 16 777 216 |
    | Выбранный проектом Store | 16 777 346 |
    | Обычный LZMA2 со словарём 1 МиБ | 68 394 |

    На этом примере выбранная эвристика пропускает уменьшение размера примерно на 99,6%. Сохранить Store как baseline, но перед исключением компрессоров выполнить быстрый LZMA2 probe на нескольких участках и проверить межфайловые повторы. Число выше относится только к проверенному синтетическому примеру.

12. **Всегда оставлять кандидата для небольших наборов.**

    Место: `src/core/TaskMatrixGenerator.cpp:180–181`. Для данных менее 10 МиБ удаляются кандидаты с оценкой памяти выше 352 МиБ. Минимальный LZMA2 64 МиБ оценивается в 960 МиБ, Delta и BCJ тоже отсеиваются. В Safe небольшие PE/медиа/некоторые бинарные наборы могут остаться без задач. Проверка на BMP размером 2048 байт дала 0 кандидатов и ошибку CLI. Небольшой текст успешно обработался оставшимися PPMd-кандидатами.

    Исправление: уменьшать словарь, а не удалять все подходящие алгоритмы. Всегда оставлять недорогой LZMA2 и Store. `optimalDictMB` сейчас вычисляется в строках 164–171, но не используется.

13. **Сделать поиск многоступенчатым и ограниченным бюджетом.**

    `runQuickProbe()` копирует целиком первый файл верхнего уровня. Для одного огромного файла это полный повтор работы; для дерева с файлами только в подпапках выборка пуста. `quickProbePercent` не задаёт фактический размер выборки. Некоторые кандидаты исключаются только из-за сбоя probe.

    Предлагаемый порядок: дешёвый baseline → репрезентативные выборки разных категорий и участков → несколько лучших семейств → полный тест → финальная проверка. Размер выборки ограничивать байтами и временем; сохранить baseline при сбое выборки. В Strict/Deep режимах сделать эвристическое исключение кандидатов явной настройкой, поскольку оно может пропустить лучший вариант.

    Добавить лимит времени, минимальный полезный выигрыш и выбор цели: минимальный размер / баланс времени и размера / ограничение памяти распаковки. В интерфейсе показывать несколько вариантов по этим критериям. Реальное ускорение и потерю степени сжатия измерять на наборе PE, исходников, смешанных ресурсов, WAV и уже сжатых файлов.

14. **Исправить распределение CPU и измерения.**

    `TaskMatrixGenerator::s_mtThreadCount` и `ResourceGuard::s_workerCount` остаются равными 1: их setters нигде не вызываются в рабочем коде. Engine передаёт worker index 0 при каждом запуске. В результате `-mmt=1` обычно фиксирован, а Windows affinity workers совпадает.

    Передавать индекс worker, общий CPU budget и число потоков каждому процессу. Сравнить стратегии «один многопоточный процесс» и «несколько кандидатов одновременно» на реальных данных. Принудительное исключение SMT не гарантирует ускорение во всех случаях; сделать его измеряемой опцией. Сохранить номер processor group вместе с маской для систем с несколькими группами.

    Проверку `7z t` выполнять только для претендентов на лидерство либо небольшого финального списка, с обязательной проверкой выбранного результата. Сейчас все архивы проверяются даже при `verifyArchives=false` в кандидатовом пути. Пик памяти Job Object переиспользуется между задачами worker, поэтому показатель может отражать предыдущую задачу. Телеметрия Windows берёт I/O родителя, хотя основную работу выполняет 7-Zip; macOS/Linux содержат имитацию части метрик. Не показывать имитацию как реальные значения.

**Архитектура и качество разработки**

- Выделить `RunContext`: снимок настроек, рабочие каталоги, effective input, manifest, cancellation и итог выполнения. Он устранит расхождения между фазами и упростит cleanup/resume.
- Представлять параметры кодеков типизированными структурами и строить аргументы 7-Zip в одном месте. Добавить проверку поддержки возможностей выбранной версии утилиты. BCJ2-конфигурации сейчас названы «4-stream», но не содержат явных bindings и четырёх отдельных кодеков: проверить фактическую схему, а не только успешный exit code. `bt5` в установленном 7zz 26.03 принят успешно, поэтому объявлять его универсально невалидным оснований нет.
- Проверять полный состав и хеши файлов после распаковки финального архива. `7z t` может подтвердить целостность неполного архива. В `ArchiveAssembler.cpp:206–225` результат добавления precompressed-файлов вычисляется, но успех `resPre` не проверяется; потеря этой группы может остаться незамеченной.
- Все временные списки и результаты создавать в уникальном workspace. Сейчас `main_list.txt` и `precomp_list.txt` имеют фиксированные имена в системном temp; распаковка и препроцессинг обходят пользовательский scratch.
- ProcessManager: ограничить накопление stdout, добавить timeout, отменять группу процессов и завершать её после grace period, обрабатывать EINTR/ошибки wait/chdir. На Windows исправить quoting обратных слешей и кавычек и передавать явный executable path. POSIX fork запускается из нескольких потоков; дескрипторы требуют close-on-exec и управляемого наследования. Где подходит, использовать posix_spawn.
- Использовать библиотеку JSON с валидацией схемы для пресетов, сессий и экспорта. Сейчас парсеры ищут подстроки, неполные поля становятся нулями, JSON экспорта не экранирует flags. Ограничить имя пресета одним безопасным компонентом пути перед чтением/записью/удалением.
- Создать общую CMake-библиотеку core вместо повторной компиляции для приложения и тестов. Флаги оптимизации задавать по конфигурации и target: Debug сейчас получает `-O3` либо `/O2`. GUI-режим задавать compile definition из CMake вместо независимого `__has_include`. Linux GUI требует проверки OpenGL linkage; toolchain содержит локальные абсолютные пути.
- Нужны интеграционные тесты с реальным 7-Zip: полный проход, шифрование, тома, SFX, препроцессинг, resume, отмена нескольких workers, отказ записи и распаковка с проверкой manifest. Тесты `... || true`, обход пустого массива и ручная имитация pruning создают ложное чувство покрытия. В CI отдельно запускать ASan/UBSan и проверку гонок, а также Windows-сборку и тесты совместимости на заявленных версиях архиваторов.
- Инициализировать Git-репозиторий, добавить `.gitignore`, закрепить версии и происхождение сторонних утилит, хранить лицензии и контрольные суммы, автоматизировать выпуск. Сборочные каталоги, дублированные бинарники и архив истории чата отделить от исходного дерева.
- Синхронизировать README с реализацией: встроенная распаковка payload уже не реализована, What-If содержит mock, resume не работает, а «100% WinRAR compatible» не доказано текущими тестами. PROJECT_MEMORY считать историей разработки, а не свидетельством работоспособности.

**Предлагаемая последовательность работ**

1. Исправить PE overflow, единицы RAM, результат CLI, безопасную замену выходного файла и lifetime GUI callbacks. Добавить регрессионные проверки этих ошибок.
2. Ввести RunContext и общий бюджет ресурсов; согласовать отмену, workspace, препроцессинг, manifest и параметры финального архива.
3. Довести восстановление сессий, многотомность, SFX и секреты; добавить интеграционные тесты и честный What-If.
4. Затем менять стратегию поиска: probes, адаптивные словари, отбор кандидатов, баланс CPU и проверку только полезных результатов. Сравнивать размер, время, пиковую RAM и объём записи на одинаковом корпусе данных.

Самая перспективная оптимизация сейчас — устранить неверные исключения кандидатов и повторную бесполезную работу. Увеличивать словари и глубину перебора до исправления этих проблем будет дорого и не даст предсказуемого результата.
