# Следующий план UltraArch Studio: RAM и снижение дисковых записей

Дата: 2026-10-10. Целевая платформа: Windows 10/11 x64, нативный MSVC. Документ описывает будущие изменения; создание плана не означает их реализацию. Базовая сборка и измерения сохранены в [отчёте от 9 октября](roadmap-implementation-2026-10-09.md).

Основная цель нового этапа — сократить временные записи и число временных файлов без ухудшения сжатия, проверки содержимого и восстановления сессий. Ускорение — отдельный возможный результат, а не обязательное обещание. Низкое потребление RAM само по себе не является целью: свободная память полезна для параллельности и временных данных.

## Что уже есть и что остаётся

Реализованы ограничение словаря LZMA по полезному solid-потоку, отдельная политика PPMd, сокращение турнира маленьких групп, защищённые варианты PE, capability single-flight/cache, совместное уточнение PPMd, история длительности, планирование групп и прогресс. Дополнительная группировка по сходству экспериментальная и выключена по умолчанию: на проверенном тексте она ухудшила размер, поэтому выиграл исходный конкурент.

Есть потоковая проверка через изолированный verify-worker и pinned 7z.dll. Она вычисляет SHA/CRC без полного дерева восстановленных файлов. По умолчанию сохраняется Disk-проверка; Streaming остаётся экспериментальным. Это декодирование, а не сжатие кандидатов в RAM. Сейчас кандидаты создаются через 7z.exe как обычные файлы; настройки порога RAM-группы и бюджета RAM-хранилища отсутствуют.

Открыты дальнейшее сокращение дорогого PE-поиска, точность ресурсных оценок, более гибкий порядок файлов, ручная GUI/DPI-приёмка, Windows 11, внешние распаковщики и физические fault-сценарии. Ограничение дисковых задач сейчас регулирует конкурентность, а не МБ/с. CPU Sets экспериментальны; Large Pages и IPO не включаются без доказательств пользы. Происхождение инструментов проверено, но приложение и worker не подписаны.

На одном Test.7z новый Balanced дал 367 238 968 байт за 1298,130884 с, пик committed memory дерева 12,93 ГиБ. Ultra7z дал 367 383 626 байт за 2850 с по GUI. Это разные backend и один вход; всеобщего превосходства результаты не доказывают. Подробнее: [измерения](optimization-roadmap-2026-10-09.md).

## 1. Сначала измерить, куда идут записи

Разделить отчёт на анализ/распаковку входа, пробы, полные кандидаты, проверку, сборку и публикацию. Для каждого этапа записывать логические файловые байты чтения/записи, число созданных и удалённых файлов, текущий/пиковый scratch, память, длительность и число процессов.

Отдельно учитывать IPC, буферы RAM, записи результатов и checkpoint. Текущий GetProcessIoCounters не считать измерением NAND-записей SSD. Добавить точный учёт собственных файловых потоков и дополнительный короткий ETW-контроль дисковых записей. Системные дисковые счётчики и SMART использовать только как сопутствующие данные: они включают другие процессы, а SMART host writes не равны физическим NAND writes.

Windows кэширует файловое I/O. Поэтому отсутствие файлового трафика в новом слое, снижение process I/O и снижение физической записи на диск — разные утверждения. Обычная выделенная RAM также может попасть в файл подкачки. Не отключать pagefile и не обещать нулевых SSD-записей; отслеживать paging и доступную физическую память.

Проверка готовности: небольшой воспроизводимый набор показывает стоимость каждого этапа; IPC не подписан как дисковая запись. Сохранены исходные показатели Disk для последующих парных сравнений.

## 2. Общее хранилище временных кандидатов

Отделить кандидата от обязательного filesystem path. Ввести внутренний ArtifactRef с RAM- или Disk-хранилищем, длиной, сроком жизни и состоянием проверки. CompressionSpec и идентификатор параметров сжатия остаются общими; транспорт и версия worker фиксируются отдельно в provenance и совместимости сессии.

RAM-хранилище должно поддерживать чтение, Seek, Write и SetSize, ограниченные рост и число объектов. Использовать порционные буферы с учётом capacity, без копирования целого архива при каждом увеличении. Сохранять один общий неизменяемый вход группы для нескольких кандидатов, когда он уже доступен в памяти. Сначала подключить к абстракции существующий Disk-путь, сохранив его поведение.

Ограничивать не только несжатый размер группы: множество крошечных файлов увеличивает заголовки и metadata. Отдельно ограничить число файлов, фактический размер выходного буфера и суммарную память. Нельзя заранее считать выходной архив меньше входа.

Проверка готовности: существующий Disk-путь даёт прежние результаты; RAII освобождает reservations и буферы при любой ошибке. Seek/SetSize, переполнение, пустые файлы и Unicode проверены без запуска большого корпуса.

## 3. Изолированный encoder-worker с RAM-потоками

Создать отдельный encode-worker на pinned 7z.dll. Интерфейсы IOutArchive/UpdateItems и входных/выходных потоков уже описаны в vendored headers. Наличие интерфейса не доказывает совпадение с CLI: это нужно подтвердить прототипом.

GUI не загружает encoder DLL в свой процесс. Worker подключается к общему Job Object, получает конфигурацию и вход через ограниченный протокол и возвращает статус, размер, метрики и handle результата. Буферы принадлежат worker либо явно учитываемой shared memory; приватные shared handles не наследуются посторонними процессами. Большие данные не сериализуются в JSON/base64. Для начала допустим один worker на активную группу; параллельные кандидаты допускаются только по общему бюджету.

Начать с LZMA1/LZMA2 без шифрования и дополнительных фильтров. Затем проверить PPMd, BZip2/Deflate, Delta, BCJ/BCJ2, контексты, сортировку, solid и шифрование. Для каждой поддерживаемой конфигурации согласовать свойства DLL с текущей CompressionSpec/CLI, включая метаданные и упаковку заголовков. Неподтверждённые варианты исполнять прежним Disk-путём с объяснением причины. Внешние препроцессоры пока используют Disk.

При завершении кандидата декодировать RAM-архив в ограниченные SHA/CRC sinks; содержимое и набор путей проверять полностью. Финальный выход сохраняет существующую обязательную проверку выбранного режима. Наличие успешного тестирования архиватора не заменяет сверку manifest.

Пароли передавать через приватный канал; не включать в аргументы, логи, ID или checkpoint. Отмена работает через callback, а при неответившем codec — завершением worker после установленного срока. Crash/OOM/timeout — ресурсные или процессные ошибки, не доказательство неподдержанного метода. Capability cache должен учитывать способ исполнения, а не слепо переносить результат CLI на новый wrapper.

Проверка готовности: для одинаковых параметров Disk и RAM сохраняют содержимое, методы и размер; при детерминированных метаданных проверять побайтовое совпадение. Любое отличие размера объяснить до включения RAM-пути для этого семейства. Повреждённый RAM-кандидат не может стать лидером. GUI остаётся жив при аварии worker.

## 4. GUI, бюджет памяти и переход на диск

Предлагаемые настройки, пока не реализованы:

- «Маленькие группы в RAM»: выключено/автоматически/включено. В первой экспериментальной поставке выключено по умолчанию.
- «Максимальный размер группы»: логарифмический ползунок с точным числовым вводом, например 1–256 МиБ. Размер означает несжатую группу, не размер словаря.
- «RAM для временных данных»: отдельный подбюджет, например 128–4096 МиБ либо Auto. Он входит в общий предел приложения, не прибавляется сверх него.
- В preview и прогрессе: фактическое хранилище, занятая/зарезервированная RAM, запись временных файлов и причины перехода на диск.

Диапазоны — проектное предложение; значения по умолчанию выбрать после коротких измерений. Все настройки проходят GUI/JSON/пресеты/CLI, типизированную валидацию и проверку совместимости resume.

Расчёт admission: память кодека, вход группы, выходные буферы, metadata, проверка, IPC, ядро/GUI и запас ОС. В текущей системе Job limit ограничивает детей, но не всю память GUI/core: новый общий учёт должен закрыть этот пробел. Не учитывать shared memory дважды и не создавать по копии группы на каждый кандидат. Мониторить available physical memory и system commit; фактическая загрузка чужих программ может измениться во время поиска.

При дефиците сначала прекратить новый RAM-admission и освободить проигравших. Затем использовать Disk. Поток может перейти из RAM на диск только с сохранением позиции и всех уже записанных байтов; иначе корректно повторить кандидат на диске. Событие явно записывается в отчёт, его стоимость учитывается. Spill не доказывает неподдержанность конфигурации.

Проверка готовности: параллельные группы не превышают резерв, отмена освобождает память, несжимаемые данные не растят буфер без предела. Ресурсный fallback сохраняет корректность; сценарий low-memory не вызывает бесконечные повторы одного кандидата.

## 5. Победители, checkpoint и финальная публикация

Проигравшие RAM-кандидаты освобождаются без создания пробных архивов на диске. Текущий лидер живёт в RAM, пока хватает подбюджета. Готовый победитель группы материализуется один раз в приватный durable artifact для существующей сборки нескольких методов. Промежуточные сохранения разрешены только как выбранный компромисс между resume и объёмом записи.

Checkpoint различает «проверен в RAM» и «проверен и сохранён». После перезапуска потерянный RAM-кандидат снова считается незавершённым, а не готовым победителем. Сохранять завершённые группы и лучшего durable-лидера; после аварии пересчитать только недолговечную часть. Журнал публикации, проверки чужих изменений и исходный архив остаются защищёнными.

Сначала SFX и тома финализируются существующим Disk-механизмом. Их поддержка не требует хранить весь итоговый архив в RAM. После перехода на новый транспорт повторить password/header encryption, SFX, volumes, Unicode/long paths и recovery на границах публикации.

Проверка готовности: при нормальном исполнении проигравшие поддерживаемые RAM-кандидаты не создают файлов содержимого. После crash результат восстанавливается из durable checkpoint без ложного resume. Финальный размер включает заголовки всех блоков и проходит полную сверку.

## 6. Следующий уровень: входные группы без полной распаковки на диск

Первая версия RAM-кандидатов убирает запись пробных архивов, но не первоначальную распаковку входного 7z. RAM-кэш уже распакованных файлов экономит главным образом повторное чтение. Эти эффекты нужно различать.

Для полного предложения пользователя добавить слой InputEntry/ContentSource, предоставляющий данные из файла или ограниченного RAM-потока. Listing и manifest сохраняют относительные пути, пустые папки, тип и SHA, не требуя materialized path для каждой записи. Decoder callback направляет допустимые небольшие записи в RAM, остальные — в приватную папку. Группы строятся по manifest; при смене типа/размера или переполнении бюджета выполняется контролируемый spill.

Не пытаться произвольно извлекать каждый файл из solid-архива повторным запуском decoder: сначала проверить, что потоковый обход не повторяет декодирование целых блоков. Многократная стоимость декодирования может перечеркнуть пользу. Для очень большого solid-входа разрешён консервативный Disk-fallback с понятной причиной.

Сохранить лимиты распаковки, счётчик файлов, защиту от traversal, ADS и reparse, обнаружение изменения входа, ExactBytes и неизменный manifest. Изменение слоя источников затрагивает resume и verifier; оно идёт отдельным этапом после стабильного RAM-output. Preprocessing и неподдерживаемые архивные операции остаются файловыми до отдельной адаптации.

Проверка готовности: малый архив может пройти поддерживаемый путь без временного распакованного дерева и пробных файлов. Для гибридного входа метрики точно показывают долю RAM и Disk. Финальный результат независимо восстанавливается в обычном 7-Zip.

## 7. Другие улучшения поиска и сжатия

### PE и дорогие группы

Развивать последовательный выбор графа/контекстов/словарей по нескольким целым PE разных архитектур и размеров. Текущий консервативный отбор оставляет много защищённых вариантов при недостаточной пробе; это защищает качество, но сохраняет длинный этап. Адаптивно увеличивать выборку только когда стоимость оправдана, сравнивать несколько finalists на полном объёме. Full сохраняет полный допустимый поиск. Улучшение подтвердить коротким независимым PE-набором и одной затронутой группой, без повторения 62 полных запусков.

### Уточнение по выигрышу и цене

Для Fast/Balanced добавить бюджет уточнения на группу и объяснимую остановку после длительного отсутствия улучшения. Использовать историю стоимости с доверительным запасом; холодная история не должна вытеснять защищённые семейства. Режим минимального размера/Full не получает скрытый тайм-аут. GUI показывает, сколько байтов выиграл очередной шаг и сколько времени он стоил.

### Порядок файлов, сходство и дубликаты

Существующая similarity меняет состав групп, а не гарантирует произвольный порядок внутри backend solid-блока. Сначала доказать реальный порядок через DLL, затем сравнить несколько детерминированных порядков: исходный, расширение/размер, точные дубликаты рядом, ограниченная сортировка по сходству. Исходный вариант всегда конкурент. SHA-дубликаты можно совместно хранить в RAM, но все имена и пустые записи должны остаться в архиве. Сходство не равно тождеству; кэш кандидата требует полного состава и байтов, а не только sketch.

### Политика выбора результата

Добавить отдельную цель «компактный архив с ограничением памяти распаковки». Сейчас большой словарь может быть приемлем для создателя, но неудобен получателю. Ограничение декодерной памяти должно учитывать реальные свойства словарей и граф BCJ2. Это явный компромисс размера, а не замена MinimumSize.

Другая опция — «выбрать более простой вариант при разнице не больше X байт/процентов»: меньше память декодера или быстрее распаковка. Применять только при явно выбранной цели, с полным отображением уступки по размеру. Измерять распаковку на коротких наборах; не подменять измерение оценкой кодека.

## 8. Ресурсы, надёжность и удобство

- Улучшить оценки памяти по семействам и измеренным пикам с консервативным запасом. Не снижать резерв до текущего Working Set: будущая аллокация кодека ещё может быть впереди. Сохранять hard Job limit и отдельный запас системной памяти.
- Диагностировать ожидание: CPU/RAM/диск, callback/worker, сборка/проверка. Watchdog использует несколько сигналов; неподвижный процент или CPU=0 сами по себе не доказывают зависание. Дать экспорт компактной диагностики и контролируемый retry/skip.
- Разделить в GUI обещания: процессные I/O, временные файловые записи и измерения накопителя. Не показывать выдуманный процент продления срока службы SSD.
- Сделать отчёт повторяемости: SHA исходника/EXE/DLL, параметры, итоговый размер, время, файлы/папки, метод проверки, fallback и версии схем. Не сохранять пароли.
- Добавить безопасный просмотр мусора сессий: размер, дата, active/incomplete/completed, что будет потеряно при удалении. Не удалять по возрасту активные данные и эталоны; очистку выбирать явно.
- Проверить диагностические ошибки OOM декодера и сообщения недостатка RAM, диска и неподдержанного codec. Это направления проверки, а не утверждение о найденном новом дефекте.
- Завершить GUI-приёмку: DPI 100/150/200%, два монитора, RU/EN, длинные строки, tray/drag-drop, cancel/pause/skip/assemble, импорт пресетов, история сессий и путь с Unicode.
- Завершить Windows 11, внешние целевые 7-Zip/WinRAR, CI MSVC/installed smoke, физический disk-full и power-loss на выделенном тестовом томе. Цифровая подпись — отдельная работа с сертификатом владельца; её нельзя объявлять готовой по SHA.

CPU Sets/processor groups, Large Pages, IPO и долгоживущий encoder-пул рассматривать после измерения конкретного bottleneck. RAM-worker может выполнять несколько задач, но усложнять постоянный пул только ради предположения об ускорении не нужно. Precomp/SREP откладываются до обратимого формата и доказанного восстановления; это отдельная совместимость, не обычный параметр стандартного 7z.

## Проверки без многочасового перебора

1. Unit/contract: RAM-store Seek/SetSize/лимиты, reservations, transport identity, checkpoint и классификация fallback.
2. Native DLL/CLI parity: текст, PE x86/x64, WAV/BMP, несжимаемые данные, много мелких файлов, пустые файлы/папки; LZMA1/2, PPMd, фильтры и BCJ2 проверять по мере включения.
3. Fault: low-memory, расширение выходного буфера, авария worker, cancel/timeout, закрытие приложения и восстановление. Обязательна проверка освобождения reservations.
4. Короткие парные Disk/RAM сравнения без параллельных сборок и других компрессоров. Зафиксировать backend, параметры, порядок файлов и режим кэша. Для основных небольших случаев сделать по три повтора; писать время, память и файловый/дисковый трафик отдельно.
5. MSVC Debug/Release, установленный пакет, Unicode/long paths, streaming/Dual, SFX/volumes/password и recovery после каждого соответствующего набора изменений.
6. Один полный контроль после завершения значимого набора изменений. Повтор нужен при смене поиска/компрессии/финализации, а не после правки документа или подписи ползунка. Серию из 62 больших запусков автоматически не возобновлять.

Готовность RAM-этапа: поддерживаемые проигравшие кандидаты не материализуются на диске; выход полностью восстановим; размер не ухудшен из-за смены транспорта; memory/fallback честно отражены. Снижение физических записей подтверждается только отдельным дисковым измерением. При отсутствии выигрыша в скорости функция может оставаться полезной по записи, но это должно быть видно в отчёте.

## Порядок исполнения

Сначала метрики и ArtifactRef/Disk-контракт. Затем минимальный RAM encoder-worker, бюджет и GUI, durable winners/resume. После native parity и fault-проверок расширить семейства. Далее — гибридная распаковка входных групп, затем дополнительные улучшения поиска/порядка и пользовательских целей. GUI/системную приёмку проводить по мере появления соответствующих функций.

Самая ранняя самостоятельная поставка — экспериментальный RAM-output для маленьких групп, с текущим файловым входом и Disk-fallback. Полное предложение пользователя завершено только после гибридного RAM-input. Сроки и проценты экономии выбрать после прототипа и замеров; сейчас они не подтверждены.
