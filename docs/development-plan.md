# План развития UltraArch Studio после 2.1

> Исторический план от 4 октября. Актуальный порядок доработок, исправлений и приёмки находится в [едином плане доводки](implementation-plan.md).

Дата: 2026-10-04. Целевая платформа продукта — Windows 10/11 x64. План основан на текущих исходниках и docs/history/2026-10-04-fixes.md. Документ фиксирует исходный план от 4 октября. Актуальная реализация и фактическая приёмка описаны в [состоянии реализации](implementation-status.md). Оценки — предварительные человеко-дни одного разработчика с доступом к Windows, без обещания календарных сроков.

Основная цель: уменьшить время и дисковую нагрузку поиска, расширить доступную матрицу в пределах общего бюджета ресурсов и сохранить обязательную проверку содержимого. Измерять отдельно размер результата, время поиска, время финализации, пиковую committed memory, прочитанные/записанные байты и максимум занятого scratch.

**1. Подтвердить Windows-поведение и зафиксировать точку сравнения.**

Существующий workflow собирает MSVC Debug/Release, но его выполнение ещё не подтверждено. Создать Git-репозиторий, сохранить исправленную 2.1 и запускать проверки в Windows CI. Расширить проверку установленного пакета: Unicode в пути к самому EXE и bin, запуск из другой текущей папки, длинные пути, read-only выход, вложенные Job Objects, одновременный OOM нескольких процессов, отмена во время проверки, SFX и тома. Обычные тесты не должны незаметно пропускать обязательный 7-Zip/SFX в релизной конфигурации.

GUI проверить на Windows 10 и 11: сворачивание, закрытие, отмена/skip/pause/assemble, неверные настройки, перенос между мониторами с разным DPI. Отдельный тест должен принудительно завершать приложение во время записи checkpoint и на границах публикации файлов. Сохранность исходника и возможность восстановления прежнего выхода обязательны.

Создать benchmark runner и корпус с SHA-256 manifest: исходники, PE x86/x64, BMP/WAV, уже сжатые медиа, смешанная папка, повторяющиеся блоки, множество мелких файлов, большие solid-данные. Для RAM/worker-тестов использовать несколько доступных бюджетов. Записывать версии EXE/DLL, CPU, RAM, диск, все параметры и идентификатор набора. Повторять выбранные сравнения минимум трижды, сравнивать медиану; описывать условия прогрева файлового кэша.

Готовность: Windows suites и установленный пакет проходят; результаты benchmark сохраняются в JSON/CSV и воспроизводятся. Не обещать проценты ускорения до этих замеров.

**2. Один manifest вместо повторных сканирований и хеширования.**

Сейчас fingerprintInput повторно вызывает ContentAnalyzer и полный checksum, а coordinator затем снова анализирует файлы и вычисляет contentChecksum. При предобработке добавляются дополнительные проходы. Ввести InputManifest: относительный путь, тип записи, размер, категория, энтропия, SHA-256; отдельно — сведения о файловой идентичности/времени для диагностики изменений.

За один начальный проход по содержимому вычислять hash и брать образец для анализа заголовка/энтропии. Файлы и пустые каталоги обходить один раз. AnalysisSummary строить из manifest. Fingerprint набора формировать из его канонической сериализации, не перечитывая содержимое.

На Windows SHA-256 реализовать через CNG с RAII и повторным использованием algorithm provider. Для native тестового стенда сохранить переносимую реализацию за тем же интерфейсом. Замерить throughput; не предполагать, что SHA-256 автоматически быстрее FNV на любой машине. Финальный повторный проход для обнаружения изменения входа сохраняется. Кэш по size/mtime не должен заменять полную проверку в строгом режиме.

Manifest сделать общим для кандидатов, проверки, resume и preview. В GUI отдавать небольшой immutable EngineSnapshot со счётчиками, а не копировать весь AnalysisSummary с files при каждом кадре. Прогресс анализа публиковать с ограниченной частотой.

Готовность: один начальный полный проход для обычного неизменённого входа; отсутствие повторных глубоких обходов на кадрах GUI; обнаружение изменения байтов, включая изменение без изменения размера. Новый checksum/schema инвалидирует несовместимые checkpoint явно.

Файлы: ContentAnalyzer, FileUtils, OptimizerEngine; новые InputManifest/Hasher/EngineSnapshot.

**3. Типизированные параметры и стабильная идентичность кандидатов.**

Сейчас память оценивается regex по строковым флагам. Генерация, валидация, экспорт и CLI должны использовать одну CompressionSpec: методы, граф фильтров/потоков BCJ2, dictionaryBytes, fastBytes, matchFinder, matchCycles, lc/lp/pb, solid и compressionThreads. Шифрование добавлять отдельным runtime secret; пароль не включать в сериализуемую спецификацию и config ID.

Compiler преобразует CompressionSpec в аргументы 7-Zip. Оценка памяти рассчитывается из структурированных параметров и всех потоков, а не из regex. Ввести типы Bytes/MiB/Seconds для API, где сейчас легко смешать единицы.

У кандидата должны быть стабильный config ID и отдельный индекс очереди. Resume сопоставлять по config ID и версии schema, не по порядковому номеру после фильтрации. Для каждой версии/хеша инструмента кэшировать проверенные возможности. Новые сочетания параметров сначала проверять на маленьком входе и малом словаре под ResourceGuard; неподдерживаемые конфигурации исключать с объяснением.

Готовность: семантически одинаковые настройки дают одинаковые аргументы/ID; все конфигурации проходят real-tool smoke; ошибочные значения отклоняются до большого запуска. Старые CLI profile aliases поддерживаются через документированное отображение, без скрытой смены поведения.

Файлы: Types, SettingsJson, TaskMatrixGenerator, SessionManager; новые CompressionSpec/SevenZipArgs/ToolCapabilities.

**4. Более эффективный поиск и использование общего RAM/CPU-бюджета.**

Текущее ограничение ramLimit/workers при генерации исключает тяжёлые конфигурации, которые можно выполнить отдельно. Генерировать конфигурации, помещающиеся в общий доступный бюджет с запасом, и планировать реальную конкуренцию по reservation RAM и CPU tokens. Workers — верхняя граница параллельности, а не обязательное деление памяти на равные части. Тяжёлые варианты запускать в отдельной фазе, чтобы они не голодали в очереди. Общий Windows Job Object оставить последней защитой.

Разделить SearchMode (Fast/Balanced/Exhaustive), цель выбора результата (минимальный размер либо самый быстрый результат в допуске к лучшему) и политику предобработки. Ввести параметр допуска размера для Balanced; минимальный размер оставить доступной явной целью. Exhaustive означает полный перебор заданного пространства; при time budget отчёт должен говорить об ограниченном поиске.

Поиск: дешёвый Store/LZMA2 baseline → репрезентативный probe → полные проверки нескольких финалистов из разных семейств → уточнение параметров вокруг лидеров. Расширить полезные размеры словарей, включая промежуточные значения, и проверить fastBytes/threads/solid. Не приравнивать лучшую категорию по байтам к лучшему общему методу.

Улучшить probe: стратификация по категориям и размерам, сохранение расширений и целых небольших файлов, ограничение времени probe и объёма образца. Для фильтров PE учитывать, что склейка произвольных фрагментов искажает адреса и структуру; сохранять кандидатов этой семьи для полной проверки. Сохранять baseline и разнообразие финалистов даже при слабом результате образца. Измерять, как часто pruning пропускает лучшую конфигурацию полного поиска.

После появления лидера: критерий остановки по бюджету и стоимости оставшегося поиска; логировать причину остановки. Хранить измеренную peak memory по конфигурации/версии инструмента и классу входа, применять консервативный запас. OOM не должен приводить к бесконечным повторным попыткам.

CPU: сначала сравнить режимы auto affinity и без принудительной affinity. Дальше прототип CPU Sets для гибридных/многогрупповых CPU, с обнаружением возможностей системы и fallback. Не считать SMT/P-ядра всегда лучше или хуже без benchmark. Для фоновой работы добавить выбор приоритета; не менять глобальные настройки Windows.

Готовность: есть сценарий, где тяжёлый кандидат выполняется отдельно; суммарные CPU tokens и reservations соблюдаются; queue не голодает. Предварительная цель Balanced — уменьшить медиану времени поиска минимум на 30% при ухудшении размера не более 1% на каждом зафиксированном наборе относительно полного перебора той же матрицы. Это критерий проверки прототипа, не обещание результата. Если цель не достигнута, скорректировать алгоритм/порог и сохранить полный поиск.

Файлы: TaskMatrixGenerator, OptimizerEngine, ResourceGuard, ProcessManager; новые SearchPlanner/ResourceScheduler.

**5. Меньше копий, контроль scratch и восстановление после аварии.**

Сейчас предобработка копирует всё дерево на каждый этап. Перейти к представлению input overlay: неизменённые записи ссылаются на оригиналы, изменяемые ресурсы получают независимую копию. Каждый изменённый файл обрабатывать транзакционно: исходная копия → tool → проверка → принятие или откат. Строить общий archive manifest из оригинальных и обработанных записей. Не применять hard links к файлам, которые внешний tool меняет in-place. Только после измерений решать, как материализовать overlay для обычного 7z CLI или использовать update callback.

Решение принять ресурс должно учитывать не только уменьшение его сырых байтов, но и размер/стоимость конечного сжатия на тестовом корпусе. Показывать список изменённых файлов, удаляемых метаданных и статистику. Политика ExactBytes остаётся вариантом без предобработки; OptimizeResources выбирается отдельно. Семантическую корректность изображений нельзя доказать одним 7z t — для поддерживаемых форматов нужны собственные проверки или сравнение декодированных данных.

WorkspaceManager контролирует принадлежность файлов запуску, quotas для распаковки (суммарные байты, число файлов, размер отдельного файла), текущий scratch и свободное место на томах scratch/output. Предварительная оценка по archive listing полезна, но runtime-ограничения обязательны: размеры метаданных могут быть неизвестны или недостоверны. Включить обработку reparse points/junctions, конфликтующих имён и путей вне workspace.

PublicationTransaction получает durable journal с фазами Prepared/Verified/BackingUp/Publishing/Committed и перечнем созданных/резервных файлов. До разрушительного шага фиксировать намерение, после него — состояние. При следующем старте предлагать безопасное восстановление принадлежащих приложению операций. Не удалять неизвестные старые каталоги автоматически. Многотомная публикация всё равно не становится атомарной; журнал уменьшает последствия аварии.

Определить контракт NTFS: сейчас проверяются обычные байты файлов. Зафиксировать поведение ADS, ACL, sparse files, hard links и reparse points. Поддержку включать отдельными возможностями с round-trip тестами; обнаруженные неподдерживаемые данные должны отображаться до старта, а не считаться проверенно сохранёнными.

Готовность: неудачный preprocess не меняет оригинал/предыдущую принятую копию; лишние полные копии исчезают на корпусе; quotas останавливают распаковку; crash injection на каждой фазе публикации позволяет сохранить/восстановить прежний выход.

**6. GUI, который объясняет результат и не блокируется на анализе.**

Вынести What-if и анализ в отменяемую фоновую задачу. Для входных архивов preview сначала использует listing/оценку, а при необходимости — ограниченную распаковку, показывая её стоимость. Пока задача работает, окно реагирует на ввод/отмену. Заменить фиксированные 2048-байтовые path buffers на std::string с ImGui stdlib helper; длинные пути проверить на Windows.

GuiModel должен разделять черновик настроек и snapshot активного запуска. В GUI добавить CPU threads, timeout, search time budget, произвольный допустимый solid, а также точные значения памяти из импортированного пресета. Устранить округление/ограничение импортированных настроек без явного уведомления. CLI/GUI/JSON проходят одну валидацию.

Показывать фазу, её прогресс, финализацию отдельно от поиска, текущую RAM и свободное место, ожидаемые расходы scratch, активные задачи и причину отказа/отсечения. Итог: реальный размер и список выходов, расход времени по фазам, лучшая конфигурация и что не было выполнено. ETA показывать как приблизительную оценку, учитывая разные семейства кандидатов.

История сессий: resume, сохранить лидера, удалить принадлежащий workspace. Сначала реализовать явные действия движка, потом добавлять кнопки «Повторить»/«Выбрать этот результат». Для многократных заданий очередь — отдельная поздняя функция, а не усложнение одного RunContext. Исправить смешение RU/EN и проверить DPI на реальных мониторах.

Готовность: при анализе большой папки нет длительного блокирования UI; импорт/экспорт поддерживаемых настроек не меняет значения; выход/ошибки доступны без чтения внутренних логов. Все действия проверяются на Windows.

**7. Воспроизводимый релиз и диагностика.**

Toolchain/versions фиксируются. Tool manifest содержит версию, SHA-256, источник получения, лицензию и возможности. Для явно указанного --tools каталога ошибка поиска должна быть явной, без незаметного переключения на другую установку из PATH. Отдельно проверить подписи/происхождение существующих бинарников и транзитивные notices.

Добавить CMakePresets и Windows-сценарий одного запуска configure/build/test/package. Разделить пользовательский portable ZIP и developer/test ZIP; сейчас тестовые EXE входят в основной пакет. Рассмотреть IPO/LTO и размер EXE после измерений, сохраняя символы диагностики отдельно. Подпись релиза — при наличии сертификата.

Ошибки сделать структурированными: phase/tool/exit code/Win32 error/category, краткая формулировка, путь к подробному логу. Лог и crash report писать в доступный пользовательский каталог; диагностический экспорт маскирует секреты. Автоматическую отправку не добавлять. Поддерживаемые распаковщики и их версии проверять отдельно, прежде чем писать заявления о совместимости.

Готовность: пакет собирается из чистого checkout; проходит установленный smoke; tool identity совпадает с manifest; пользователь получает понятную причину ошибки; ZIP не содержит временных сессий/личных данных.

**8. Проверка содержимого без полной записи распакованных данных на диск.**

Текущая полная контрольная распаковка надёжна для поддерживаемых обычных файлов, но записывает весь набор данных. Прототип отдельного verify-worker.exe с закреплённой версией 7z.dll: IInArchive/IArchiveExtractCallback передаёт каждый восстановленный поток в SHA-256 sink. Проверяются пути, размеры, checksum, каталоги, operation result, шифрование, тома и SFX. Память/процессы worker ограничиваются Job Objects; отмена и timeout остаются независимыми от GUI.

Сначала оставить существующую дисковую проверку fallback и сравнить оба verifier на одинаковых архивах, включая повреждения и неправильный пароль. Binary API/IPC отделить от построчного отображения stdout; secret передавать worker через ограниченный канал, не логировать. Потоковая проверка не отменяет декомпрессию/CRC и сравнение с входным manifest.

Не заменять её простым 7z x -so для всех файлов: нужен контроль границ и принадлежности каждого потока. Пофайловые внешние запуски могут повторно распаковывать solid-блоки и ухудшать производительность.

Готовность: оба verifier согласны на корпусе; новый выявляет намеренно неправильные/повреждённые файлы; scratch для контрольной распаковки не зависит от суммарного размера восстановленных файлов, но память декодера учитывается. После этого решать, можно ли объединить проверки CRC и содержимого в один проход.

**Порядок поставки.**

- Итерация A: этап 1, быстрый EngineSnapshot/фоновый preview, InputManifest и CompressionSpec. Результат — подтверждённая Windows-база и меньше повторного I/O без изменения стратегии выбора лидера.
- Итерация B: staged search, общий scheduler, новые критерии выбора, overlay preprocessing, journal/quota. Результат — измеряемое ускорение и управляемые ресурсы с тестами восстановления.
- Итерация C: полноценный UI управления сессиями, финальная упаковка/диагностика, потоковый verifier после отдельного прототипа.

Каждая задача — небольшое отдельное изменение с тестом реального сценария, сравнением с baseline и возможностью отключить новую стратегию. Рефакторинг API отделять от изменения алгоритма поиска. Не отключать проверку содержимого ради показателей скорости; не добавлять новые кодеки/Precomp/SREP без ясного контракта восстановления и совместимости.
