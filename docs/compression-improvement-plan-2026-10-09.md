# Улучшение UltraArch по результатам сравнения с Ultra7z

Дата: 2026-10-09. Платформа: Windows 10/11 x64, MSVC. Приоритет пользователя — качество сжатия; скорость, нагрузка, надёжность и удобство также измеряются. Этот план продолжает план от 2026-10-04 и уточняет работу над поиском по новым фактическим данным.

После завершённого нового Balanced актуальные измерения и очередность следующих улучшений вынесены в [дальнейший план оптимизации](optimization-roadmap-2026-10-09.md). Описанные ниже исходные ограничения относятся к началу работы; выполненные изменения и проверки перечислены в [отчёте прогресса](compression-progress-2026-10-09.md).

## Отправная точка и критерии

Эталон сравнения — сохранённый Test.7z без TTF, SHA-256 `530b3e4d6377b154bc8313ebc3b9be00f50376390c5f27ead3a678059259cea7`. 10 144 файла, 890 папок, 953 500 040 распакованных байт.

- Ultra7z: 367 383 626 байт, GUI 2850 с, пик committed memory дерева 22 846 214 144 байта.
- UltraArch: 401 731 104 байта, 1691,506 с, пик committed memory дерева 24 591 998 976 байт.
- Оба результата независимо проверены по путям, размерам, SHA-256 файлов и составу папок.

Подробные условия и ограничения измерений — в [отчёте сравнения](ultra7z-comparison-2026-10-09.md). Это один прогон с разными стратегиями поиска, backend и сохранённым кэшем. Он показывает конкретный разрыв по сжатию, но не определяет универсальный рейтинг программ.

Первый рубеж качества на этом неизменном входе: результат не больше **367 383 626 байт**. Цель улучшения: строго меньший архив при успешной независимой проверке. Копирование результата Ultra7z не считается достижением: новый архив должен быть создан нашим поиском из исходных файлов. Выигрыш на этом наборе не заменяет проверку на независимом корпусе.

Размер имеет приоритет в режиме Size. Ограничения памяти, времени и фоновой нагрузки задаются отдельно. Нельзя обещать одновременно лучший размер, минимальное время и минимальную память для всех данных: требуется измерять отдельные режимы и выбирать выигрышные сочетания затрат.

## 1. Сохранить и объяснить базовый результат

Сохранить идентификаторы входа, текущего EXE/backend, настройки, manifest и результат Ultra7z как внешний эталон. Разобрать `etw-7z-events.jsonl` и журналы: отделить пробные команды от финальной сборки, сопоставить списки файлов, методы, словари, фильтры, время и exit status там, где события позволяют. PID сопоставлять вместе со временем создания: повторное использование PID не должно объединять разные процессы. Не считать событие или запуск отдельным уникальным кандидатом.

Сопоставить реальные solid-блоки обоих итоговых архивов, их методы и группы файлов. ETW начат после начала оптимизации; неполную раннюю часть явно отмечать. По последней команде или пробному размеру не объявлять конфигурацию победителем.

Затем выполнить измерения, меняя одну стратегию за раз: текущая матрица; LZMA1 и расширенные фильтры; группировка; адаптивный поиск. Сравнивать итоговый размер, время, CPU, committed memory, transfer counters и scratch. Время поиска и проверки фиксировать отдельно. Не смешивать счётчики переноса данных с физическим трафиком SSD.

Готовность: есть воспроизводимая карта покрытых и недостающих вариантов, а вклад новых стратегий подтверждается отдельными прогонами.

## 2. Исходный архив как допустимый победитель

Для уже существующего совместимого 7z в режиме Exact добавить проверенного исходного кандидата. Если перепаковка больше, итоговый выбор сохраняет исходное сжатие. При явном запросе другого формата, томов, SFX, пароля или другого состава данных исходный архив не считается автоматически подходящим.

Переиспользуемый исходник проходит обязательную проверку manifest. Перед публикацией повторно проверить его идентичность; публикация выполняется тем же journal/lock механизмом. Отчёт должен различать улучшение, сохранение исходного архива и преобразование формата. Нельзя писать «оптимизировано», если улучшения нет.

Готовность: при неизменном формате и требованиях результат не больше исходника; тестируются изменение входа, несовместимый формат вывода и восстановление публикации. Это предотвращает ухудшение, но не устраняет разрыв с Ultra7z.

## 3. Расширить типизированные параметры сжатия

Подтверждённые ограничения текущего кода:

- `Codec` не содержит LZMA1, BZip2 и Deflate.
- `TaskMatrixGenerator` генерирует PPMd только до 256 МиБ и order 16, хотя `CompressionSpec` допускает order 32 и более крупную память.
- BCJ2 в текущей матрице ограничивает основной словарь 8 МиБ.
- Для Delta проверяются отдельные значения, а не все 1–32.
- Основные solid-варианты — разделение по расширениям и блок 128 МиБ; непрерывный solid не входит автоматически в полную матрицу многофайлового входа.

Первое расширение: LZMA1; правильные отдельные диапазоны lc/lp/pb и match finder для LZMA1/LZMA2; непрерывный solid; BCJ/BCJ2 с размером основного словаря по данным и бюджету; PPMd orders до 32 и память по бюджету. Затем добавить BZip2/Deflate и Delta 1–32 там, где backend подтверждает поддержку и есть польза на данных.

Не переносить строковые флаги Ultra7z вслепую. Проверять возможности pinned backend 26.03, компиляцию графа, ограничения параметров, оценку памяти и восстановление данных. Обновить schema/config IDs и явно инвалидировать несовместимые checkpoint. Секреты не включать в ID или журнал команд.

Готовность: новые семейства присутствуют в preview, имеют стабильные ID, корректно проходят test/декодирование и улучшают хотя бы соответствующий набор данных. Вклад в размер Test.7z измерен отдельно.

## 4. Выбор методов для групп и совместная сборка

Сейчас UltraArch выбирает один набор параметров для всего входа. Ultra7z в наблюдаемом прогоне обновлял общий архив отдельными группами с разными методами. Это приоритетная гипотеза для сокращения разрыва по сжатию.

Строить группы по manifest: содержимое/сигнатура, расширение, размер, повторяемость. PE, текст, несжатые медиа и уже сжатые данные получают подходящие семейства кандидатов. Расширение — признак для поиска, не гарантия типа и не основание менять байты.

Для каждой группы выбирать метод, затем собирать стандартный 7z с несколькими solid-блоками. Сравнивать сгруппированный результат с общим solid-кандидатом, потому что группировка может уничтожить полезные межфайловые совпадения. Учитывать размер заголовков и окончательный размер архива; суммы пробных архивов недостаточно.

Приватная сборка, исключение повторов/пропусков, пустые папки, Unicode и длинные пути, resume по группам. Проверка общего manifest обязательна после сборки. Пароли, SFX и тома требуют проверки финализации нескольких методов; до этого неподдерживаемые сочетания отклоняются явно.

Готовность: групповая и общая стратегии соревнуются на полном входе; выбранный итог соответствует manifest и не превышает эталон Ultra7z на фиксированном наборе.

## 5. Умный поиск и управление нагрузкой

Сначала доказать качество широкой матрицы, затем сокращать затраты её поиска. Сэмплы брать из нескольких частей крупных файлов, разных файлов и типов; сохранять необходимые заголовки фильтров. Размер выборки, размер словаря и solid-блок — разные параметры.

По пробам отбирать несколько перспективных вариантов каждой группы/семейства и проверять их на полном объёме. Не отбрасывать семейство только по одной неудачной пробе. Полный поиск остаётся контрольным режимом для проверки пропущенных победителей.

Использовать имеющийся параллельный планировщик проб и расширить его на группы. Задачи резервируют память и CPU; тяжёлая сборка конкурирует за тот же общий бюджет. Быстрые задачи не должны зависать за длинной задачей при свободных ресурсах. Корректировать оценку памяти по измерениям, сохраняя жёсткое ограничение Job Objects.

Фоновый режим отдельно задаёт бюджет CPU, памяти и дисковых операций. Не считать низкий приоритет ограничением CPU или I/O. Large Pages включать только после измерений: флаг не доказывает фактическое применение или пользу. Прогресс, pause/resume/cancel и журнал объясняют выбор и отбрасывание вариантов.

Готовность: адаптивный режим достигает заданного допуска относительно полного поиска на корпусе, с меньшими затратами; режим Size сохраняет полный вариант без эвристического сокращения. Для заявлений об экономии памяти/нагрузки нужны соответствующие измерения.

## 6. Проверка и сравнительная приёмка

После каждого изменения — релевантные unit/integration checks, затем native MSVC Debug/Release и installed-package smoke для готового пакета. После изменения сборки нескольких методов повторить worker/Dual, Unicode/long paths, отмену/OOM/recovery, SFX и тома. Проверять реальное восстановление, не только argv.

Корпус: текущий смешанный набор, PE x86/x64, текст/исходники, WAV/BMP, сжатые медиа, много мелких файлов и повторяемые большие данные. Версии, параметры и SHA фиксируются. Измерения обеих программ — по возможности с одинаковым backend для объяснения причин, а также с их штатным backend для сравнения продукта. Минимум три повтора ключевых режимов, медианы времени и пиков ресурсов, согласованные условия кэша и дисков.

Публиковать результат по каждому набору. В Size целевой размер не больше Ultra7z на сопоставимом входе; строгий выигрыш требуется для заявления «лучше сжимает». Фоновый режим оценивается отдельно. Не объявлять универсальное превосходство, если остаются проигрыши или непроверенные условия.

## Порядок первых изменений

Сначала сформировать карту финальной сборки Ultra7z и добавить проверенный исходный кандидат. Следующий отдельный набор изменений — LZMA1, непрерывный solid и сильные BCJ2-варианты. Замерить вклад. Затем реализовать группы и несколько методов в одном архиве. Адаптивное сокращение поиска вводить после установления качества полной стратегии.

Новые проценты выигрыша и календарные сроки до этих измерений не обещаются. Самые важные первые результаты: отсутствие ухудшения входного архива, сокращение разрыва в 34 347 478 байт и независимо подтверждённое сжатие не хуже Ultra7z.
